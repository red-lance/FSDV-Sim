Part II · Mission controllers·accel_driver.py

fs_autonomy/accel_driver.py 166 lines ours ACCELERATION mission: closed-loop speed hold + brake

The simplest controller, and the best one to understand first because every other controller reuses its exact skeleton (imports, parameter pattern, mission gate, tick loop). Full docstring, unmodified:

"""
accel_driver -- autonomy node for the eufs_sim2 ACCELERATION mission.

The sim's VCU hands control over once ASState reaches DRIVING, but nothing
publishes /cmd by default -- so the car just sits there. This node fills that
gap: drive straight under closed-loop speed control, brake to a stop past the
finish line.

The sim consumes ONLY drive.acceleration and drive.steering_angle from /cmd
(eufs_sim2/src/control.cpp); drive.speed is ignored entirely. Speed is
therefore regulated here: a P controller on the odometry speed error outputs
an acceleration command. The vehicle model applies negative acceleration as
braking and clamps it to zero once the car has stopped, so holding a brake
command cannot reverse the car.
"""

Two sentences carry the whole design rationale. "The sim consumes ONLY drive.acceleration and drive.steering_angle" is upstream bug #1 (Part VIII has the exact 11-line C++ file that proves it) — it's why speed control has to happen here, in our node, instead of just telling the sim "go 8 m/s." "the vehicle model... clamps it to zero once the car has stopped" is the fact that makes holding a brake command safe — we rely on it instead of writing our own zero-crossing logic.

Imports and parameters

import math

import rclpy
from rclpy.node import Node
from std_msgs.msg import String
from nav_msgs.msg import Odometry
from ackermann_msgs.msg import AckermannDriveStamped


class AccelDriver(Node):
    def __init__(self):
        super().__init__("accel_driver")   # node's name on the ROS graph

        self.declare_parameter("odom_topic", "/odom")
        self.declare_parameter("mission", "ACCELERATION")
        self.declare_parameter("target_speed", 8.0)
        self.declare_parameter("finish_distance", 75.0)
        self.declare_parameter("accel_limit", 3.0)
        self.declare_parameter("brake_limit", 4.0)
        self.declare_parameter("kp", 1.5)
        self.declare_parameter("stop_speed", 0.1)
        self.declare_parameter("brake_hold", 1.0)
        self.declare_parameter("publish_rate", 50.0)

Every parameter here is a knob, not a magic number — that's deliberate: config/accel_params.yaml sets these at launch, so tuning never touches this file. odom_topic defaults to /odom (ground truth) but is what flips to /odometry/filtered for the EKF experiment (Part IX, §11 of the field guide). finish_distance: 75.0 is straight from the FS rulebook's Acceleration event distance.

State variables

self.driving = False      # is ASState == DRIVING right now?
self.start_xy = None      # pose captured the instant DRIVING began
self.position = None      # latest odom position
self.speed = 0.0          # latest odom forward speed
self.distance = 0.0       # metres travelled since start_xy
self.braking = False       # latched once finish_distance is crossed
self.stopped = False

Notice self.braking is a latch, not a recomputed condition: once the car crosses 75 m it stays in "braking" mode even if self.distance later reads something odd (e.g. under odometry drift). That's a deliberate one-way state machine, not an oversight — you don't want a noisy distance reading to un-brake a car mid-stop.

Wiring — the three lines that touch the sim

self.pub = self.create_publisher(AckermannDriveStamped, "/cmd", 10)
self.create_subscription(String, "/sim/ros_can/state_str", self.on_state, 10)
self.create_subscription(
    Odometry, self.get_parameter("odom_topic").value, self.on_odom, 10)
self.create_timer(1.0 / rate, self.tick)

This is the entire coupling to eufs_sim2 — one publisher, two subscriptions. The 10 is the ROS queue depth (how many unread messages to buffer per subscriber before dropping old ones); at 50 Hz control loops this is generous headroom.

The mission gate — on_state

def on_state(self, msg):
    # engage only when OUR mission is selected AND the VCU has released
    # control -- this is what links the Foxglove mission dropdown to this
    # node; other mission controllers can run alongside and stay idle
    mine = ("AMIState: %s" % self.mission) in msg.data
    driving = mine and "ASState: DRIVING" in msg.data

    if driving and not self.driving:
        # just entered DRIVING -- latch the start pose and reset the run
        self.start_xy = self.position
        self.distance = 0.0
        self.braking = False
        self.stopped = False
    elif not driving and self.driving:
        self.get_logger().info("Left DRIVING -- stopping.")

    self.driving = driving

msg.data is a plain string like "AMIState: ACCELERATION ASState: DRIVING" — the sim's state machine publishes its whole state as text, and we do a substring check rather than parsing an enum. Crude, but it means we never need the sim's C++ headers to read its state. Note the edge detection: driving and not self.driving only fires once, on the transition into DRIVING — that's where the run resets. Every following tick just sees driving == True and does nothing special here.

The control loop — tick()

def tick(self):
    if not self.driving:
        return                              # <-- the whole "obey the RES" contract

    if not self.braking and self.distance >= self.finish_distance:
        self.braking = True

    target = 0.0 if self.braking else self.target_speed
    accel = self.kp * (target - self.speed)                 # P-control
    accel = max(-self.brake_limit, min(self.accel_limit, accel))

    if self.braking and abs(self.speed) < self.stop_speed:
        accel = -self.brake_hold           # hold rather than coast to zero

    cmd = AckermannDriveStamped()
    cmd.drive.acceleration = float(accel)
    cmd.drive.steering_angle = 0.0          # straight-line event
    self.pub.publish(cmd)

Read this as one sentence: "every 20 ms, if driving, compute the speed error, scale it by kp, clamp it to what the car can physically do, and send it." Braking is not a separate code path — it's the same line (accel = kp * (target - speed)) with target switched to zero. That's the whole insight: cruise control and emergency braking are the same feedback loop pointed at different setpoints.

30-second summary to say out loud "accel_driver holds 8 m/s with a proportional controller on speed error, and brakes with the exact same formula once it's travelled 75 m — the target speed just switches to zero. It only ever acts while the state machine says DRIVING, so an emergency stop is obeyed automatically. Verified: holds 8 m/s, stops about 9 m past the 75 m line, matching the v²/2a physics prediction."
Why is finish_distance a latch (self.braking) instead of a live comparison?
Because odometry can be noisy or drift (§10/§11 of the field guide). If braking were re-evaluated every tick from raw distance, a noisy reading dipping back under 75 m could theoretically un-brake the car mid-stop. Latching makes "crossed the line" a one-way, permanent fact for the rest of the run — the correct semantics for a competition rule.

Part II·skidpad_driver.py

fs_autonomy/skidpad_driver.py 259 lines ours SKIDPAD mission: odometry-based figure-8, pure pursuit

Same skeleton as accel_driver.py — same imports, same parameter-declare pattern, same on_state mission gate (not re-shown; it's byte-for-byte the same idea with self.mission == "SKIDPAD"). What's new here is geometry: this controller has to know the shape of a figure-8 and where it is on the car, using only odometry.

Frame math — the trick that makes everything else simple

def yaw_from_quaternion(q):
    return math.atan2(
        2.0 * (q.w * q.z + q.x * q.y), 1.0 - 2.0 * (q.y * q.y + q.z * q.z)
    )

def rel_pose(self):
    """Current pose in the start frame (origin at start, x along initial heading)."""
    x0, y0, yaw0 = self.start_pose
    x, y, yaw = self.pose
    dx, dy = x - x0, y - y0
    c, s = math.cos(-yaw0), math.sin(-yaw0)
    return (c * dx - s * dy, s * dx + c * dy, wrap(yaw - yaw0))

yaw_from_quaternion converts ROS's quaternion orientation (4 numbers, avoids gimbal lock) into a single heading angle — we only ever need 2D heading, so this one line is the entire "quaternion math" the project needs. rel_pose re-expresses the car's absolute map position into a coordinate frame anchored at the start of the run, with x pointing along the car's initial heading. That's a standard 2D rotation (the c, s pair is cos/sin of the negative start heading). Why bother: the FS skidpad geometry (circle centers at ±9.25 m, crossing 9.8 m ahead) is defined relative to where the car starts, not in absolute map coordinates — so working in this frame means the geometry constants are just the numbers from the rulebook, with no dependence on where the car happened to spawn.

The phase state machine

ENTRY, RIGHT, LEFT, EXIT, BRAKE = "ENTRY", "RIGHT", "LEFT", "EXIT", "BRAKE"

def advance_phase(self, rx, ry):
    xc = self.entry_distance                 # crossing point is at (xc, 0)

    if self.phase == ENTRY and rx >= xc:
        self.phase = RIGHT
        self.turn_angle = 0.0

    elif self.phase in (RIGHT, LEFT):
        cy = -self.radius if self.phase == RIGHT else self.radius
        phi = math.atan2(ry - cy, rx - xc)     # angle around the circle center
        if self.prev_phi is not None:
            self.turn_angle += wrap(phi - self.prev_phi)   # accumulate signed angle
        self.prev_phi = phi

        full = self.laps * 2.0 * math.pi - 0.05
        if self.phase == RIGHT and self.turn_angle <= -full:
            self.phase = LEFT
        elif self.phase == LEFT and self.turn_angle >= full:
            self.phase = EXIT

    elif self.phase == EXIT and rx >= xc + self.exit_distance:
        self.phase = BRAKE

The clever bit is lap counting by angle, not by crossing a line. Each tick, the code measures the car's bearing phi around whichever circle's center it's currently orbiting, and accumulates the change in that bearing (wrap() keeps the difference in (-π, π] so a wraparound from +π to −π doesn't register as a huge jump). Two full laps clockwise is exactly −4π radians; that's the full threshold. This is more robust than "did we cross a specific point" because it doesn't care about the car's radial error — it just keeps summing rotation until enough of it has happened.

Where the target point comes from

def target_point(self, rx, ry):
    xc = self.entry_distance
    if self.phase in (ENTRY, EXIT, BRAKE):
        return (rx + self.lookahead, 0.0)     # ahead on the centerline y=0

    cy = -self.radius if self.phase == RIGHT else self.radius
    phi = math.atan2(ry - cy, rx - xc)
    dphi = self.lookahead / self.radius        # arc length -> angle, at this radius
    phi_t = phi - dphi if self.phase == RIGHT else phi + dphi
    return (xc + self.radius * math.cos(phi_t), cy + self.radius * math.sin(phi_t))

On the circles, the pure-pursuit target isn't just "a fixed point ahead" — it's a point on the ideal circle, a fixed arc length (lookahead metres) further around. Converting arc length to an angle at a known radius is just angle = arc / radius — that's dphi. The sign flip (phi - dphi vs phi + dphi) is what makes the right circle get driven clockwise and the left counter-clockwise.

tick() — steering and speed, same pure-pursuit formula as trackdrive

tx, ty = self.target_point(rx, ry)
# rotate the target from the start frame into the CAR's current body frame
dxb = math.cos(-ryaw) * (tx - rx) - math.sin(-ryaw) * (ty - ry)
dyb = math.sin(-ryaw) * (tx - rx) + math.cos(-ryaw) * (ty - ry)
alpha = math.atan2(dyb, dxb)
ld = math.hypot(dxb, dyb)
steer = math.atan2(2.0 * self.wheelbase * math.sin(alpha), ld)

This is the pure-pursuit steering law explained in the field guide §5 — identical formula to trackdrive's. The only difference between the two controllers is where the target point comes from: here it's computed from known geometry in the odometry frame; in trackdrive it comes from whatever cones are currently visible.

30-second summary to say out loud "Skidpad drives a fixed figure-8 whose shape comes from the rulebook, tracked entirely from odometry — no cones involved. We work in a frame anchored at the start pose so the geometry constants are just the numbers from the rules. Lap counting sums signed rotation angle rather than checking crossings, which is more robust to path error. Because this controller trusts odometry for geometry rather than perception, it's the one most exposed to state-estimation drift — which is exactly what the EKF experiment measured."
Why sum rotation angle instead of just checking "am I back near the entry point"?
A distance-to-start check can't tell two laps from zero laps — both put the car back near the same point. Angle accumulation directly counts how much circle has been driven, which is what "two laps" actually means.

Part II·trackdrive_driver.py

fs_autonomy/trackdrive_driver.py 297 lines ours TRACK_DRIVE + AUTOCROSS: steering from cone perception

The first controller that never looks at a map — it steers from car-relative cone detections. Same skeleton again (imports, parameters, mission gate); what's new is a third subscription and the target-selection logic.

Classifying a cone

def classify(cone):
    """Highest-probability colour label for a cone."""
    probs = {
        "blue": cone.blue_prob,
        "yellow": cone.yellow_prob,
        "orange": cone.orange_prob,
        "big_orange": cone.big_orange_prob,
        "unknown": cone.unknown_prob,
    }
    return max(probs, key=probs.get)

Each cone message doesn't carry a single "color" field — it carries five probabilities (this is exactly what a real perception model would output too: confidence per class). classify() just takes the most likely one. This is the seam where a real YOLO detector would plug in — its output has the same shape.

Picking a steering target from a cone list

def pick_target(self):
    left, right = [], []
    for cone in self.cones_msg.cones:
        x, y = cone.point.x, cone.point.y
        r = math.hypot(x, y)
        if x < 0.2 or r > self.max_cone_range:
            continue                          # behind us or too far to trust
        label = classify(cone)
        if label == "blue":   left.append((r, x, y))
        elif label == "yellow": right.append((r, x, y))
        elif label in ("orange", "big_orange"):
            (left if y > 0.0 else right).append((r, x, y))

    left.sort(); right.sort()          # nearest first (tuples sort by r)

    if left and right:
        candidates = []
        for (_, bx, by), (_, yx, yy) in zip(left[:3], right[:3]):
            mx, my = (bx + yx) / 2.0, (by + yy) / 2.0
            candidates.append((math.hypot(mx, my), mx, my))
        for dist, mx, my in candidates:
            if dist >= self.min_target_dist:
                return (mx, my)
        return (candidates[-1][1], candidates[-1][2])

    if left:
        _, cx, cy = left[0]
        return (cx, cy - self.half_track)      # blue = left edge: aim right of it
    if right:
        _, cx, cy = right[0]
        return (cx, cy + self.half_track)      # yellow = right edge: aim left of it
    return None                                    # nothing usable -- blind

Walk this in three cases, worst to best:

  • Nothing visible (both lists empty) → returns None → the caller treats this as "blind."
  • One side visible — steer toward a point offset half a track width (1.75 m) from the visible cone, on the correct side. This is a sane fallback, not a failure: if you can see the left edge, you can infer roughly where the right edge must be.
  • Both sides visible — take up to 3 nearest pairs, compute each pair's midpoint, and pick the first one far enough ahead (min_target_dist) — this avoids picking a target so close it produces a jerky, oversized steering angle.

Bug found by the Monte-Carlo sweep, not by inspection The original code timed "how long has it been blind" from the last time a cone message arrived at all — but an empty detection array is still a message. A perception source that sees nothing keeps publishing empty arrays at full frame rate, so that timer kept getting reset and never elapsed: the car crept forward at minimum speed forever, 335 m off the track before we noticed, in the first zero-detection sweep. The fix: track the time of the last usable target, not the last message. A blind car now genuinely stops.
30-second summary to say out loud "Trackdrive never uses odometry for steering — only for lap counting. It classifies visible cones by color probability, pairs the nearest blue and yellow, and pure-pursuits toward the midpoint, falling back to a half-track offset if only one side is visible. Verified: 3 out of 3 laps, 10 cm max deviation, zero cones hit. And this controller directly caught a real bug in our own code — a blind car that should have stopped kept creeping — found by the very Monte-Carlo sweep this platform exists to run."
Why classify cones from probabilities instead of a single label field?
Because that's what a real detector outputs — confidence per class, not a certainty. Consuming the same shape of data the sim produces means a real YOLO model's output (also probabilities per class) can replace the sim's cones with zero code change downstream — see field guide §9, Path 2.

Part III · State estimation·wheel_odometry.py

fs_autonomy/wheel_odometry.py 85 lines ours wheel speeds → covariance-stamped twist, for the EKF

The EKF (robot_localization, an off-the-shelf package) expects a standard ROS message shape for velocity input: TwistWithCovarianceStamped. The sim's wheel-speed message is its own custom type (eufs_msgs/WheelSpeedsStamped), so this node's whole job is translation.

def __init__(self):
    super().__init__("wheel_odometry")
    self.declare_parameter("wheel_radius", 0.2525)  # m (ads-dv config)
    self.declare_parameter("speed_unit", "rps")     # "rps" (eufs_sim2) | "rpm" (real car)
    self.declare_parameter("vx_stddev", 0.05)       # m/s, trust in wheel-derived vx
    self.declare_parameter("vy_stddev", 0.1)        # m/s, nonholonomic slack

    radius = self.get_parameter("wheel_radius").value
    unit = self.get_parameter("speed_unit").value
    self.circumference = 2.0 * math.pi * radius
    self.per_rev = self.circumference / (60.0 if unit == "rpm" else 1.0)
Upstream quirk this parameter works around The sim's message field documents wheel speed as "RPM", but the actual physics code (eufs_core.cpp) computes v_x / tyre_circumference with no ×60 — that's revolutions per second, not per minute. speed_unit defaults to "rps" for the sim; the same node runs unmodified against a real car's CAN bus by switching it to "rpm".
def on_wheel_speeds(self, msg):
    rear_mean = 0.5 * (msg.speeds.lb_speed + msg.speeds.rb_speed)

    out = TwistWithCovarianceStamped()
    out.header.stamp = msg.header.stamp     # preserve source (sim) time
    out.twist.twist.linear.x = rear_mean * self.per_rev
    out.twist.twist.linear.y = 0.0
    out.twist.covariance = self.cov
    self.pub.publish(out)

Why the rear wheels, not front: the front wheels are steered, so their speed differs from the car's own forward speed by 1/cos(steering) — an extra correction we'd rather not need. The rear wheels are undriven by steering geometry, so their mean speed is the car's forward speed directly. linear.y = 0.0 encodes the nonholonomic assumption — a car doesn't slide sideways — as a measurement, with vy_stddev giving the EKF a little slack rather than treating it as an exact zero.

30-second summary to say out loud "This node exists purely to speak the EKF's language: it takes the sim's custom wheel-speed message, corrects for the RPM-vs-rev/s mismatch we found, and republishes a standard velocity-with-uncertainty message from the mean rear-wheel speed."

Part III·imu_frontend.py

fs_autonomy/imu_frontend.py 66 lines ours fills in IMU covariance the sim leaves at zero 
def on_imu(self, msg):
    msg.angular_velocity_covariance = self.gyro_cov
    msg.linear_acceleration_covariance = self.accel_cov
    msg.orientation_covariance = self.orient_cov
    self.pub.publish(msg)

This is the whole node's logic, in four lines. The reason it needs to exist at all: an EKF weighs each sensor by how much it's told to trust it — that trust is carried as a covariance number inside the message itself, not in the filter's own config. The sim's IMU plugin generates realistic noisy values (Part VIII has the exact injection code) but never fills the covariance fields — they arrive as zero. A covariance of zero is a mathematical claim of "this reading is perfect," which would make the filter blindly over-trust the IMU over everything else. This node stamps the actual configured uncertainty onto the stream before it reaches the filter.

self.orient_cov = [0.0] * 9
for i in (0, 4, 8):
    self.orient_cov[i] = 1000.0   # deliberately huge: "don't trust this"

One more deliberate choice: orientation covariance is set enormous rather than accurate. Our EKF config (Part VI) doesn't fuse orientation at all — this is belt-and-braces, making sure that if anything downstream ever did look at it, the huge number screams "ignore me" rather than silently looking trustworthy.

30-second summary to say out loud "Four lines, but they matter: an EKF trusts a sensor exactly as much as its message says to, and the simulator was shipping zero — meaning 'perfect sensor' — for every IMU reading. This node fills in the real, configured uncertainty before the filter ever sees the data."

Part IV · SIL harnesses·odom_corruptor.py

fs_autonomy/odom_corruptor.py 56 lines ours shared odometry error model, used by all 3 SIL harnesses

Not a node — a plain importable class. Its whole purpose: let a harness compute metrics against the true state while publishing a corrupted one, so a controller can be tested against realistic dead-reckoning error without needing a real EKF running.

class OdomCorruptor:
    PARAMS = (
        ("odom_pos_noise", 0.0),              # m, white
        ("odom_yaw_noise_deg", 0.0),          # deg, white
        ("odom_vel_noise", 0.0),              # m/s, white
        ("odom_drift_m_per_sqrt_min", 0.0),   # random-walk position drift
        ("odom_yaw_drift_deg_per_sqrt_min", 0.0),
    )

    def __init__(self, node, rng, dt):
        gp = lambda k: node.get_parameter(k).value
        self.rng = rng
        self.pos_noise = gp("odom_pos_noise")
        self.yaw_noise = math.radians(gp("odom_yaw_noise_deg"))
        self.vel_noise = gp("odom_vel_noise")
        # random-walk step size scales with sqrt(dt) -- standard Brownian-motion math
        self.drift_q = gp("odom_drift_m_per_sqrt_min") * math.sqrt(dt / 60.0)
        self.yaw_drift_q = math.radians(
            gp("odom_yaw_drift_deg_per_sqrt_min")) * math.sqrt(dt / 60.0)
        self.drift_x = 0.0; self.drift_y = 0.0; self.drift_yaw = 0.0

Why sqrt(dt): this is the defining property of a random walk (Brownian motion) — if you take many small independent random steps, the total distance wandered after time t grows with √t, not t. A parameter given in "metres per √minute" is exactly calibrated so a longer sim step doesn't accidentally produce more or less total drift for the same wall-clock duration — it's the standard unit physicists use for exactly this kind of noise.

def corrupt(self, x, y, yaw, v):
    """Advance drift one step; return the estimated (x, y, yaw, v)."""
    g = self.rng.gauss
    self.drift_x += g(0.0, self.drift_q)       # accumulates -- this IS the random walk
    self.drift_y += g(0.0, self.drift_q)
    self.drift_yaw += g(0.0, self.yaw_drift_q)
    return (x + self.drift_x + g(0.0, self.pos_noise),
            y + self.drift_y + g(0.0, self.pos_noise),
            yaw + self.drift_yaw + g(0.0, self.yaw_noise),
            v + g(0.0, self.vel_noise))

Two separate error sources, added together: white noise (a fresh random offset every call, doesn't accumulate — represents sensor jitter) and drift (added to a running total every call — represents integrated heading/position error that never resets, the signature failure mode of dead reckoning). rng.gauss(0, σ) draws one sample from a normal distribution with that standard deviation — calling it with σ=0 (the parameter default) always returns exactly 0, so this class is a complete no-op unless a harness deliberately dials the knobs up.

30-second summary to say out loud "Every SIL harness scores itself against the true, uncorrupted physics state, but can publish a deliberately noisy version of it to the controller under test — white noise plus a random-walk drift, the standard model for how a real dead-reckoning estimator degrades over time. This one small class is shared by all three harnesses, so 'how much odometry error can this mission tolerate' is answered identically across accel, skidpad, and trackdrive."
Why use a separate RNG stream (seed+1) for odometry error instead of reusing the harness's main one?
So sweeping the odometry knobs never resamples the same random numbers used for, say, the perception error model. Two independent streams mean you can attribute a change in outcome to the exact parameter you varied — otherwise changing one knob would silently perturb an unrelated one too, through shared randomness.

Part IV·sil_skidpad.py

fs_autonomy/sil_skidpad.py 154 lines ours SIL harness for skidpad_driver — kinematic bicycle

Skidpad turns, so the 1D model from sil_accel won't do. This harness steps the kinematic bicycle model — the standard minimal car model used across the whole project (also inside sil_trackdrive, byte-identical).

WHEELBASE = 1.53
STEER_MAX = 0.37
STEER_TAU = 0.15      # actuator lag [s]

def step(self):
    self.t += DT
    # actuator lag, then kinematic bicycle; same no-reverse rule as the sim
    self.steer += (self.steer_cmd - self.steer) * DT / STEER_TAU
    a = 0.0 if (self.v <= 0.0 and self.a_cmd < 0.0) else self.a_cmd
    self.v = max(0.0, self.v + a * DT)
    dyaw = self.v / WHEELBASE * math.tan(self.steer) * DT
    self.yaw += dyaw
    self.x += self.v * math.cos(self.yaw) * DT
    self.y += self.v * math.sin(self.yaw) * DT

Read each line as one physical fact:

  • self.steer += (steer_cmd - steer) * DT / STEER_TAU — the steering wheel doesn't snap instantly to a new angle; it eases toward the commanded angle with a time constant of 0.15 s (a first-order lag, the simplest honest model of an actuator with inertia).
  • dyaw = v / WHEELBASE * tan(steer) * DT — this is the kinematic bicycle model: turning rate is forward speed times tan(steering angle), divided by wheelbase. A tighter wheelbase or sharper steering angle turns the car faster for the same speed.
  • The last two lines are just "move forward along the current heading" — standard 2D integration.

ELL_A, ELL_B, WOBBLE = 17.0, 12.0, 0.8

def build_track():
    n = 720
    center = []
    for i in range(n):
        th = -math.pi / 2.0 + 2.0 * math.pi * i / n
        px = ELL_A * math.cos(th)
        py = ELL_B * math.sin(th)
        norm = math.hypot(px / ELL_A**2, py / ELL_B**2)
        nx, ny = (px / ELL_A**2) / norm, (py / ELL_B**2) / norm  # outward normal
        w = WOBBLE * math.sin(3.0 * th)
        center.append((px + w * nx, ELL_B + py + w * ny))

An ellipse (17 × 12 m semi-axes) sampled at 720 points around its circumference, then each point is pushed outward or inward along its normal direction by a sinusoidal "wobble" (3 full oscillations per lap) — that's what turns a plain ellipse into a track with S-bends. The outward normal of an ellipse isn't just the radius direction (unlike a circle), so it's computed properly from the ellipse's gradient (px/a², py/b², normalized).

def error_at(self, r):
    """(p_detect, color_flip_prob, bearing_sigma_deg, range_sigma_frac) at range r."""
    if self.profile is None:

def sense_frame(self):
    dets = []
    c, s = math.cos(-self.yaw), math.sin(-self.yaw)
    for cones, color in ((self.blue, "blue"), (self.yellow, "yellow")):
        for cx, cy in cones:
            dx, dy = cx - self.x, cy - self.y
            bx, by = c * dx - s * dy, s * dx + c * dy    # world -> car body frame
            r = math.hypot(bx, by); th = math.atan2(by, bx)
            if r > self.sensor_range or abs(th) > self.fov_half:
                continue                                      # geometric cutoff first
            p_det, flip, b_sig, r_sig = self.error_at(r)
            if self.rng.random() > p_det:
                continue                                      # the model "misses" this cone
            if r_sig > 0.0:
                r = max(0.5, r * (1.0 + self.rng.gauss(0.0, r_sig)))
            if b_sig > 0.0:
                th += math.radians(self.rng.gauss(0.0, b_sig))
            col = color
            if flip > 0.0 and self.rng.random() < flip:
                col = "yellow" if color == "blue" else "blue"
            dets.append((r * math.cos(th), r * math.sin(th), col))

    for _ in range(self.poisson(self.fp_per_frame)):
        r = self.rng.uniform(1.0, self.sensor_range)
        th = self.rng.uniform(-self.fov_half, self.fov_half)
        dets.append((r * math.cos(th), r * math.sin(th), self.rng.choice(("blue", "yellow"))))
    return dets

This function generates one sensor frame, applying every error source in sequence to every ground-truth cone: geometric field-of-view cutoff first (hard limit — a real sensor simply cannot see behind that angle/range), then a coin-flip against the measured detection probability (a "miss"), then range and bearing noise (a "found it, but slightly wrong position"), then a color flip (a "found it, called it the wrong color"). Finally, false positives are added — phantom cones that don't exist — drawn from a Poisson distribution (the standard probability model for "how many random independent events happen in a fixed window," here "how many false detections per frame").

Poisson sampling, implemented from scratch

def poisson(self, lam):
    if lam <= 0.0:
        return 0
    limit = math.exp(-lam)
    k, p = 0, 1.0
    while True:
        p *= self.rng.random()
        if p <= limit:
            return k
        k += 1

Knuth's classic algorithm: multiply random numbers together until the product drops below e-λ; the count of multiplications is Poisson-distributed with mean λ. Implemented directly rather than pulled from a library, because Python's standard random module (used everywhere else for reproducibility) doesn't include a Poisson sampler, and adding a dependency (like numpy) just for this would break the "runs anywhere with just Python + ROS" simplicity of the harnesses.

Why simulate false positives with Poisson rather than a fixed count per frame?
Real spurious detections don't happen a fixed number of times per frame — they're rare, independent events (a shadow, a reflection, background clutter momentarily resembling a cone). Poisson is the standard distribution for "how many rare independent events in a fixed window," which is exactly this situation, and it naturally produces frames with zero false positives most of the time and occasionally two or three — matching real detector behavior far better than a constant.

        if v >= best_iou:
            best, best_iou = p, v

Standard detection-evaluation matching: for every ground-truth box, find the model's best unclaimed prediction by IoU (Intersection-over-Union — overlap area divided by combined area; 1.0 = identical boxes, 0 = no overlap). A match only counts if IoU clears a threshold (default 0.5) — this greedy, nearest-first matching is the same basic approach standard detection metrics like mAP use.

The output is exactly the shape sil_trackdrive.py's error_at() reads — this script's whole purpose is producing the JSON that other file consumes.

The one deliberate edit we made to simulator source rather than working around: the original config gave every IMU axis a noise variance of exactly 1.0 — mathematically convenient (an identity matrix) but physically absurd, about a hundred times noisier than any real automotive IMU. We replaced it with BMI088-class values (a real, common automotive-grade IMU chip's published noise specs) so the EKF experiment would be fusing plausibly realistic sensor data rather than either "perfect" or "cartoonishly bad" numbers.
