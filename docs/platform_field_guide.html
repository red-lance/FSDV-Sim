FSDV-Sim Field Guide

Everything the platform does, why it does it, and how to explain it out loud.

Sim-first development platform for Formula Student Driverless · ROS 2 Humble · repo: red-lance/FSDV-Sim · August 2026

This guide is ordered as a curriculum: each section builds on the one before. Every concept comes with the actual code from the repo, a plain-English explanation, and a “say it like this” box — a sentence you can use in a presentation verbatim. The quiz cards at the end of sections are the questions an examiner is most likely to ask; try answering before expanding.

1The big picture

The project is not "controllers that drive a simulated race car." It is a development platform: a way for a team to develop autonomy software against a simulator, verify it automatically and cheaply, and deploy the identical software to the real car's computer with zero changes.

Say it like this "Develop, verify, deploy. The controllers prove the platform is usable, the test harnesses prove the software is correct, and the containment rules prove it's portable. Everything we built is one leg of that tripod."
eufs_sim2vehicle physics · cones · state machine · sensors (own workspace, never a build dep)
⇄

⇄

Monte-Carlo runnerseeded sweeps → success-rate curves → requirements specs
Profile extractorsmeasure a real YOLO / real EKF → inject its measured errors into the loop

The load-bearing idea is the two-layer interface contract. Layer 1 is raw sensors (odometry, IMU, wheel speeds). Layer 2 is objects — car-relative cone positions with colors. Anything that produces a layer can be swapped without touching what consumes it: ground-truth cones ↔ a YOLO detector, ground-truth odometry ↔ a real EKF. We demonstrated both swaps.

Isn't this just gluing existing tools together?
Yes — deliberately. Simulators, stacks, and datasets all exist online; what doesn't exist is a verified path between them: documented interfaces, repeatable closed-loop testing, and identical-code deployment to embedded hardware. In industry that layer is called platform engineering, and every new FS team currently rebuilds it from scratch each year. Integration with evidence is the contribution.

2ROS 2 — exactly the parts we used

ROS 2 is a middleware: it lets many small programs (nodes) talk to each other by publishing typed messages on named topics. Nobody calls anybody directly — a node publishes "here is the car's speed" and whoever cares subscribes. That decoupling is what makes components swappable.

A node, anatomically

Every node in the repo has the same skeleton. This is real code from accel_driver.py, trimmed:

import rclpy
from rclpy.node import Node
from nav_msgs.msg import Odometry
from ackermann_msgs.msg import AckermannDriveStamped

class AccelDriver(Node):
    def __init__(self):
        super().__init__("accel_driver")               # node name on the graph

        self.declare_parameter("target_speed", 8.0)    # configurable at launch
        self.target_speed = self.get_parameter("target_speed").value

        self.pub = self.create_publisher(              # we SEND commands
            AckermannDriveStamped, "/cmd", 10)
        self.create_subscription(                      # we RECEIVE odometry
            Odometry, "/odom", self.on_odom, 10)
        self.create_timer(1.0 / 50.0, self.tick)       # control loop, 50 Hz

    def on_odom(self, msg):                            # callback: runs per message
        self.speed = msg.twist.twist.linear.x

def main():
    rclpy.init()
    rclpy.spin(AccelDriver())                          # hand control to ROS

Four primitives carried the whole project:

  • Publisher / subscription — one-way typed streams. The message types are generated classes: Odometry has .pose.pose.position.x, .twist.twist.linear.x, etc.
  • Timer — "call this function at 50 Hz." All our control loops are timers; callbacks and timers run one-at-a-time per node, so no locking is needed.
  • Parameters — declared per node, settable at launch (-p target_speed:=6.0) or from YAML config files. This is how one trackdrive_driver executable also runs AUTOCROSS (laps:=1), and how controllers switch odometry source (odom_topic:=/odometry/filtered).
  • Services — request/response calls, used by the sim's state machine: /set_mission, /go, /ebs, /reset. This is what makes fully headless (scripted) mission runs possible.

Discovery and DDS domains

ROS 2 nodes find each other automatically over DDS — any node on the same machine (or LAN) with the same ROS_DOMAIN_ID joins the same "bus." Powerful, and dangerous: a running simulator publishes /odom, and if a test harness also publishes /odom, the controller under test receives two contradictory realities.

Say it like this "Every automated test runs in an isolated DDS domain. It's the ROS 2 equivalent of a clean-room: collisions with a running simulator become impossible by construction, not by discipline."

Workspaces and launch files

colcon build --symlink-install builds a workspace; source install/setup.bash overlays it onto your shell. We keep two workspaces — the sim's and ours — that meet only over topics. Launch files are Python programs that start many nodes at once: autonomy.launch.py starts all four controllers, the visualization bridge, and the EKF stack, each with its YAML parameters.

Why do all four mission controllers run at the same time without fighting?
Because none of them acts until the state machine says so. Each controller subscribes to the sim's state string and engages only when its own mission is selected AND the state is DRIVING (§3). The other three stay silent. One car runs one mission at a time anyway — that's the competition format, so the software mirrors it.
What happens if two nodes publish to /cmd at once?
Both streams interleave and the car judders between two opinions — there is no arbitration in ROS 2 topics. That's exactly why mission gating matters, and why harness tests get an isolated ROS_DOMAIN_ID.

3Authority: the state machine & the RES

An autonomous race car has no driver to hit the brakes, so Formula Student moves that authority outside the car: the RES (Remote Emergency System) is a radio remote in a track marshal's hand with an E-stop (fires the Emergency Brake System) and a GO button (the final human authorization to start). Lost radio link = automatic stop.

In the sim, the RES is virtual: a Foxglove panel (named "Gross Funk" after the real hardware) or the /go service moves the VCU state machine AS_READY → AS_DRIVING; the /ebs service throws it into EMERGENCY_BRAKE. Our controllers are built under that authority — this gate is at the top of every controller:

trackdrive_driver.py — the mission gate
def on_state(self, msg):
    # engage only when OUR mission is selected AND the VCU has
    # released control; otherwise stay silent
    mine = ("AMIState: %s" % self.mission) in msg.data
    driving = mine and "ASState: DRIVING" in msg.data
    ...
    self.driving = driving

def tick(self):
    if not self.driving:
        return          # an RES stop is obeyed by construction
Say it like this "Our controllers never decide when they're allowed to drive. The state machine tells them, and the RES commands the state machine. An emergency stop is obeyed by construction, not by convention — and because the interface is just a state topic, the identical code obeys the real RES hardware on a real car."

4Controller 1 — Acceleration, or: P-control

The FS Acceleration event: standstill → 75 m straight, fast → autonomous full stop. The key constraint we discovered by reading the sim's source: the sim consumes only drive.acceleration and drive.steering_angle from /cmd — the drive.speed field is silently ignored (upstream bug #1). You cannot tell the car "go 8 m/s"; like a real car, it only understands pedals. So speed regulation is our job — a feedback loop:

accel_driver.py — the whole control law
def tick(self):
    if not self.driving:
        return

    if not self.braking and self.distance >= self.finish_distance:
        self.braking = True                    # latched: crossed 75 m

    target = 0.0 if self.braking else self.target_speed
    accel = self.kp * (target - self.speed)    # P-control on speed error
    accel = max(-self.brake_limit, min(self.accel_limit, accel))

    if self.braking and abs(self.speed) < self.stop_speed:
        accel = -self.brake_hold               # hold the brake once stopped

    cmd = AckermannDriveStamped()
    cmd.drive.acceleration = float(accel)
    cmd.drive.steering_angle = 0.0             # straight-line event
    self.pub.publish(cmd)

P-control in one sentence: command a correction proportional to the error. Going 6 m/s when the target is 8? Error = 2, so push 3 m/s² (kp=1.5). Too fast? The same formula brakes. Fifty times a second. The same three lines both cruise and stop the car — braking is just P-control toward a target of zero.

The physics check — braking from v = 8 m/s at a = 4 m/s²: distance = v²/2a = 64/8 = 8 m. Measured stop: ~84 m after braking at 75 — a 9 m stop including actuator lag. Measured-matches-predicted is the strongest sentence in any engineering presentation.

Why only P — where are the I and D terms?
We measured that we don't need them: the plant is nearly ideal (we command acceleration directly), the car holds 8 m/s with no steady-state offset and no oscillation, and stops cleanly. Integral and derivative terms fix problems we demonstrated we don't have; adding them is a two-line change if the real vehicle disagrees.
Can holding the brake command make the car reverse?
No — the vehicle model clamps negative acceleration to zero once the car is stationary (verified in the sim source, mirrored in our harnesses). A held brake is a parking brake, not reverse gear.

5Controller 2 — Skidpad, or: pure pursuit

Skidpad: a figure-8 — two laps clockwise around the right circle, two counter-clockwise around the left (radius 9.25 m), then exit. This controller drives pure geometry from odometry: it knows the figure-8 shape from the rulebook and tracks it — no cones involved. That design choice matters later (§10): it makes skidpad the controller most exposed to odometry error.

Pure pursuit in one sentence: aim at a point a fixed distance ahead on the path, and steer with the bicycle-geometry formula that would arc you through it:

# alpha = bearing to the lookahead point, ld = distance to it
steer = atan2(2 * wheelbase * sin(alpha), ld)

That formula is the whole steering law for both skidpad and trackdrive. It self-corrects: drift off the path and the lookahead point's bearing grows, steering you back. Verified against its harness: 5 cm max radial error, exactly 8π radians of turning (two laps each way), clean stop. In the full simulator (heavier physics): 0.204 m mean circle error — the gap between those two numbers is the vehicle-dynamics offset, and it becomes important in §11.

6Controller 3 — Trackdrive, or: steering from perception

Trackdrive/autocross: an unknown circuit marked by blue cones (left edge) and yellow cones (right edge). No map. The controller steers entirely from car-relative cone detections: find the nearest blue, the nearest yellow, aim at their midpoint with pure pursuit. One side missing? Offset half a track width from the side you can see. Nothing visible? Slow, hold the wheel, and stop if blindness persists.

trackdrive_driver.py — target selection (trimmed)
def pick_target(self):
    left, right = [], []
    for cone in self.cones_msg.cones:
        label = classify(cone)              # highest color probability
        if label == "blue":   left.append(cone)
        if label == "yellow": right.append(cone)

    if left and right:                      # midpoint of nearest pair
        return midpoint(nearest(left), nearest(right))
    if left:                                # one-sided fallback:
        return offset(nearest(left), -self.half_track)
    if right:
        return offset(nearest(right), +self.half_track)
    return None                             # blind

Odometry is used only to count laps (leave the start area, come back near it) and for speed feedback — never for path geometry. That makes trackdrive the mirror image of skidpad: perception-anchored where skidpad is geometry-anchored. The pair of them turns out to be a built-in science experiment (§10).

Verified: 3/3 laps on a 92 m circuit, 0.10 m max deviation from centerline, zero cones hit.

Say it like this "Trackdrive is the perception socket made real: it consumes the object layer of our interface contract, so replacing simulated cone detections with a real neural network is a pure substitution — the controller cannot tell the difference, and we proved that by feeding it three different cone sources."

7Testing: SIL harnesses & the bicycle model

SIL = software-in-the-loop. Each controller has a harness (sil_accel, sil_skidpad, sil_trackdrive) that replaces the entire simulator with ~200 lines of substitute physics. The controller can't tell: it sees the same topics. But a harness episode runs in seconds, needs no GPU, is seeded (same seed → identical run), and prints one machine-readable verdict line:

RESULT laps=3 dev_mean=0.048 dev_max=0.105 cones_hit=0 max_v=3.80 time=95.2 final_v=0.000 seed=1000

The physics inside is the kinematic bicycle model — the standard minimal car: four lines of math integrated at 50 Hz.

sil_trackdrive.py — the vehicle, complete
self.steer += (self.steer_cmd - self.steer) * DT / STEER_TAU   # actuator lag
a = 0.0 if (self.v <= 0.0 and self.a_cmd < 0.0) else self.a_cmd # no reverse
self.v = max(0.0, self.v + a * DT)
self.yaw += self.v / WHEELBASE * math.tan(self.steer) * DT      # bicycle
self.x += self.v * math.cos(self.yaw) * DT
self.y += self.v * math.sin(self.yaw) * DT

Two design rules make the harnesses scientifically honest:

  • Score against truth, publish the lie. The harness owns ground truth, so its metrics (deviation, cones hit) always use the true state — while the odometry and cone detections it publishes can be corrupted by error models (§8). The controller lives in the corrupted world; the report card is written in the true one.
  • Seeded randomness. Every random draw comes from random.Random(seed). Same seed = bit-identical episode = reproducible bugs and honest A/B comparisons. Independent error sources get independent streams (seed+1 for odometry) so sweeping one knob never resamples another.
Your test physics is fake. Why should anyone believe results from it?
Because we checked. §11 is a prediction test: the harness predicted the full simulator's behavior under measured odometry drift to within 0.01 m on the mean. Where it disagreed (worst-case error), we found the mechanistic reason and documented the fix. A model you've validated against a richer model — and annotated where it breaks — is an instrument, not a toy.

8Monte-Carlo sweeps & error models

One passing run proves little — the interesting question is "how much error can the mission tolerate?". The machinery: run_sweeps.py launches driver + harness as subprocesses on an isolated domain, N seeded episodes per parameter value, one CSV row each; plot_sweeps.py turns CSVs into success-rate curves.

# the state-estimation experiment, 20 episodes per point, 3x realtime
python3 scripts/run_sweeps.py --mission skidpad --episodes 20 --speed 3 \
    --sweep odom_yaw_drift_deg_per_sqrt_min=0,1,2,4,8 --out skid_drift.csv

The harness sensor is a parameterized error model. For perception (sil_trackdrive): detection probability per range bucket, bearing and range noise, color flips, false positives (Poisson per frame), and a latency buffer. For odometry (all harnesses, shared odom_corruptor.py): white noise plus a seeded random-walk drift —

def corrupt(self, x, y, yaw, v):
    g = self.rng.gauss
    self.drift_x   += g(0.0, self.drift_q)       # random walk: accumulates
    self.drift_yaw += g(0.0, self.yaw_drift_q)
    return (x + self.drift_x + g(0.0, self.pos_noise),
            y + self.drift_y + g(0.0, self.pos_noise),
            yaw + self.drift_yaw + g(0.0, self.yaw_noise),
            v + g(0.0, self.vel_noise))

Findings so far (each one presentation-ready)

  • Uniform detection dropout is nearly harmless. Trackdrive passes at 5% detection probability, because detections integrate across 16 Hz frames. The dangerous errors are structured: range-concentrated misses, color flips, false positives, latency.
  • Odometry drift splits the controllers exactly as architecture predicts. Trackdrive steering is immune (cones don't lie) but its odom-based lap counter produces phantom laps. Skidpad error grows monotonically with yaw drift: 0.054 / 0.199 / 0.380 / 0.558 m max at 0/2/4/6 °/√min.
  • Curves read backwards are requirements. "Success collapses below X" is a specification for the future perception or state-estimation team — derived from data, not asserted from literature.
Say it like this "Our episodes cost seconds on a laptop CPU, so we can afford thousands of closed-loop runs. Photorealistic simulators cannot — and that's why our robustness chapter exists and theirs usually doesn't."

9Perception: YOLO, FSOCO, and error profiles

The dataset: FSOCO — thousands of labeled cone photos contributed by FS teams. The model: YOLOv5-nano ("you only look once" — a single-pass detector that outputs bounding boxes + classes), trained 50 epochs on the AMZ subset: precision 0.90, recall 0.64, mAP@0.5 = 0.736, ~29 ms/frame on CPU. Five classes: blue, yellow, orange, large-orange, unknown.

Precision / recall / mAP in plain words
Precision 0.90 — of everything the model called a cone, 90% really were (few false alarms). Recall 0.64 — of all real cones, it found 64% (averaged over all distances; misses live mostly far away). mAP@0.5 — a combined score across confidence thresholds, counting a detection as correct when its box overlaps truth by ≥ 50%.

The key architectural fact: eufs_sim2 renders no camera images — its "camera" is a geometric filter over ground-truth cones (110°, 20 m, with color). So the network can't run in this loop. Instead, the platform tests perception in two composable halves:

  1. Measure the model offline, on real photos. extract_error_profile.py runs the trained network over the held-out test split and measures how it fails: P(detect) per range bucket, color confusion, bearing/range error, false positives per frame. Range comes from a classic trick — cone height is regulation-fixed, so box height in pixels → distance via the pinhole model.
  2. Replay those measured failures in the loop. The harness loads the profile JSON and corrupts its cone stream exactly the way the real model would. Downstream, the controller can't tell the replica from the real detector. The sweep then answers: do this model's specific failure patterns break the mission?
Say it like this "This is standard safety-engineering practice: characterize a component's failure statistics, then verify the system tolerates them. Nobody crash-tests every airbag chip — they qualify the part and verify the system against its spec. Our two-layer contract is what makes that decomposition legitimate."
Why not just run YOLO on simulated images?
Domain gap: a network trained on real photos sees synthetic renders as out-of-distribution, so its in-sim performance wouldn't represent reality — and eufs_sim2 has no images anyway. Measuring on real FSOCO photos and replaying the measured statistics is more honest than a pretty in-sim demo. (For LiDAR the gap is small — point clouds are geometry — which is why the Gazebo route stays defensible for the future LiDAR module.)

10State estimation: the EKF thread

Real cars don't get ground-truth position — they estimate it by fusing noisy sensors. An EKF (extended Kalman filter) keeps a state estimate (pose, velocities) and loops two steps hundreds of times a second: predict (advance the state with a motion model — uncertainty grows) and correct (blend in each sensor reading, weighted by trust — uncertainty shrinks). The trust weights come from covariances: R per sensor (carried inside each ROS message), Q for the motion model (config). An EKF is tuned, not trained.

We used the standard robot_localization package and fed it the sim's raw sensor layer — with two small adapters we had to write because of upstream quirks:

  • wheel_odometry — converts the wheel-speed message (rev/s in the sim, despite the comment saying RPM — upstream quirk) into a covariance-stamped forward velocity, from the mean of the rear wheels.
  • imu_frontend — the sim never fills the IMU message's covariance fields, and a zero covariance would make the filter blindly over-trust it; this node stamps the configured variances on.
config/ekf_params.yaml — what gets fused (dead-reckoning: no GPS, no compass)
imu0: /imu/data_cov          # fuse: yaw rate + forward acceleration
imu0_config: [false, false, false,   false, false, false,
              false, false, false,   false, false, true,
              true,  false, false]
twist0: /wheel_odometry/twist        # fuse: vx (+ vy pinned ~0: cars
twist0_config: [..., true, true, false, ...]   # don't slide sideways)

Measured (83 m mission, EKF vs ground truth): position drift 2.0 m = 2.4% of distance traveled, heading error 2.5°, velocity noise σ 0.017 m/s. Those numbers calibrated the harness knobs — the Monte-Carlo sweeps now pivot around a measured estimator.

The in-the-loop demo: the accel mission ran entirely on /odometry/filtered. The driver believed "stopped at 82.9 m"; ground truth: 82.88 m — two centimeters apart — while the EKF's absolute pose was over 80 m wrong (dead reckoning can't see teleports and its heading drift accumulates forever).

Say it like this "Absolute pose drifts without bound; relative quantities stay usable. Our acceleration controller only needs distance-from-start, so it survives dead reckoning almost perfectly. Skidpad needs absolute geometry, so it degrades — and quantifying exactly how fast is the next section."
Could we "train" the EKF on data?
Not train — tune. Q and R are static matrices. But the sim gives ground truth for free, so tuning can be automated: grid- search Q values, score each by RMSE against truth, keep the best. And when a real IMU arrives: hours of stationary logging → Allan-variance analysis → its measured noise density and bias instability go into both the filter's R and the sim's IMU config — the simulator then impersonates your actual part before the car exists.

11The prediction test — validating the method itself

The sharpest question anyone can ask: "your thousands of test runs used fake noise — why believe them?" The answer is an experiment with the structure model predicts → reality measures → compare:

  1. The SIL sweep produced a curve: skidpad circle error vs yaw drift.
  2. The real EKF measured 3.1 °/√min of yaw drift.
  3. Reading 3.1 off the curve, plus the vehicle-dynamics offset from the full-sim control run, predicts mean error ≈ 0.32 m.
  4. Then we ran skidpad on the actual EKF in the actual simulator and measured the true circle error.
Runmean (m)max (m)
SIL harness, no drift0.0150.054
Full sim, ground-truth odom (control — also the first full-sim skidpad validation)0.2040.207
Prediction at measured 3.1 °/√min (dynamics offset + SIL curve)≈ 0.32≈ 0.30 + offset
Full sim, driving on the EKF0.330.69

Verdict: the mean validated to within 0.01 m — the cheap harness is a faithful instrument. The max was ~2× underpredicted, and we know why: real EKF drift is a time-correlated bias ramp (error concentrates late in the run), while the harness knob is a white random walk that wanders both ways. The fix is already specified: a bias-ramp mode for the corruptor. A validated instrument plus a mechanistically-explained discrepancy is a stronger result than either alone.

Bonus: the mission still passed on the EKF — full entry, four laps, exit, stop; worst circle error 0.69 m against a 1.5 m half-lane.

13Cheat sheet

Numbers worth memorizing

  • Accel: holds 8 m/s, brakes at 75 m, stops ~84 m (v²/2a = 8 m + lag).
  • Skidpad SIL: 5 cm max radial error, exactly 8π rad of turn.
  • Trackdrive SIL: 3/3 laps, 0.10 m max deviation, 0 cones hit.
  • YOLO on FSOCO: P 0.90 / R 0.64 / mAP50 0.736, ~29 ms CPU.
