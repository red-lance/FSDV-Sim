§1 The 60-second pitch

Say this first, before anything technical

"We're building the software that drives a Formula Student Driverless car — not the car itself." Last semester we planned the hardware: which LiDAR, which microcontroller, which detector. That plan still stands. But none of that software can actually be tested until the hardware exists, and by then it's too late to find out the control logic is wrong.

So this phase, we built and tested the full autonomy stack — one controller per FS Driverless event, a state estimator, and a statistical test suite — entirely in simulation, but built so it plugs into real hardware later with zero code changes. We didn't just demo it working once; we ran it hundreds of times under injected sensor noise and measured exactly how much drift it can tolerate before it fails.

§2 Explain — the walkthrough

Talk through it in this order

Talk in three movements: the platform underneath (ROS), the world it runs in (eufs_sim2), then what we actually built inside that world. Each one sets up the next — don't skip the first two to get to "the cool part," the cool part only makes sense because of them.

A ROS — the platform underneath

1 What ROS actually is

ROS (Robot Operating System — we're on ROS 2 Humble, on Ubuntu 22.04) isn't an OS, it's middleware: instead of one giant program controlling the car, you write many small independent programs called nodes, and they talk to each other by publishing and subscribing to named topics, each carrying a fixed message type. A steering node never calls a perception node directly — it just subscribes to a /cones topic and reads whatever's published there, from whoever's publishing it.

2 Why that specific detail matters for us

That publish/subscribe boundary is the whole reason our "deploy unchanged" claim is even possible. Our controller doesn't know or care whether the thing publishing /cones is a simulator or a real camera+LiDAR pipeline — it only knows the topic name and message type. Swap what's on the other end of the topic, and our code doesn't need to change. That's not a nice side effect of using ROS, it's the specific property we're relying on.

B eufs_sim2 — the environment we run in

3 What it is

eufs_sim2 is a ROS 2-native vehicle simulator built for Formula Student Driverless. It's itself a ROS 2 node — a 3-DOF dynamic bicycle model of the car — with sensor plugins (LiDAR, depth camera, IMU, GPS, wheel speed) running as child nodes underneath it, each publishing its own topic exactly like a real sensor driver would.

4 It's an empty stage, not an autonomous car

Important distinction to say out loud: eufs_sim2 contains zero autonomy. A car dropped into it just sits there — nothing drives unless something external publishes a drive command. It gives us physics, sensors, and an official Autonomous System state machine (mission select → ready → driving, published as AMIState / ASState) — the same lifecycle a real competition car goes through. It does not give us a single line of driving logic. That's entirely ours.

5 How our code plugs into that state machine

The simulator never launches our code; it only announces the selected mission and state, e.g. AMIState: SKIDPAD, ASState: DRIVING. Every controller we wrote watches that one topic and self-activates only when it's both selected and cleared to drive. One launch file holds all four controllers at once — picking a mission in the sim UI, not a code change, decides which one actually takes the wheel.

C What we built inside it

6 Four mission controllers, one line each

  • Acceleration — closed-loop speed control, timed brake at the line.
  • Skidpad — pure-pursuit steering around a known figure-eight.
  • Trackdrive — perception-based pure pursuit; steers at the midpoint of the nearest blue/yellow cone pair, counts laps by watching for the orange gate.
  • Autocross — same code as Trackdrive, one lap instead of many.

7 Why closed-loop, not just "send a speed"

While building this we found the simulator's vehicle model silently ignores a directly commanded speed — it only reads acceleration and steering angle off /cmd. Command speed: 0 and the car coasts, it doesn't brake. So every controller measures actual speed and corrects it continuously (P-control) instead of trusting an open-loop command. First real bug we found, and it forced a better design.

8 State estimation (EKF)

We fuse IMU yaw-rate/acceleration with wheel-odometry-derived speed through an Extended Kalman Filter, replacing raw simulated ground-truth with a realistic filtered pose estimate — the same kind of estimate real IMU/wheel-encoder hardware would produce, with real noise and drift.

9 Why we test with a cheap model instead of only the full simulator

The full simulator is too slow to run hundreds of times. So each mission also has a lightweight software-in-the-loop (SIL) harness — same controller code, a cheap physics stand-in — with injectable sensor errors (dropout, noise, false positives, latency, drift). We checked this cheap model isn't lying to us: it predicted 0.32 m of skidpad tracking error under measured drift; the real, expensive simulator measured 0.33 m under the same conditions. That's the validation that lets us trust the fast tests.

10 The statistics, in one sentence

We ran 8 independent seeded episodes at each of six odometry-drift levels and computed a 95% confidence interval (Wilson score, the standard method for small-sample pass/fail data) on the success rate at each level — not just "it passed once."

§3 Defend — anticipated questions

The ones most likely to come back at you

HardestWhy should we believe simulation results transfer to a real car?

Answer

Two separate reasons, don't blur them. First, the architecture: our code has exactly one dependency on the simulator (message definitions), so nothing about the control logic is simulator-specific — swapping in real driver nodes is a topic-level substitution, not a rewrite. Second, the estimator: we didn't just trust simulated ground truth — we fused realistic IMU/wheel noise through an EKF, and validated our cheap test model against the full simulator to within 0.01 m. We're not claiming sim-to-real is solved; we're claiming the software we tested doesn't know it's in a simulator, which is the honest, defensible version of that claim.

Hardestn=8 per point — isn't that too small to mean anything?

Answer

It's small, and we say so explicitly — that's exactly why we report a confidence interval instead of a bare percentage. At n=8, 100% success has a 95% CI of 67.6–100%, not "100%, done." The finding we actually stand behind is the shape across the sweep: success stays flat through 8°/√min and only degrades at the extreme end, and the worst-case error grows sharply while the median stays low — a pattern that's visible even with wide individual intervals. Tightening the interval is on our future-work list; it costs roughly 4× the episodes to halve the margin, which is a compute/time tradeoff, not a methodology flaw.

ScopeYou dropped the hardware plan — isn't that a step backward?

Answer

We didn't drop it, we resequenced it. The hardware selections from last semester (VCU, LiDAR) still stand as the target platform. What changed is what gets built first: the software that has to be correct on day one of hardware bring-up, tested statistically instead of once. That's lower risk, not less ambition.

ScopeTrackdrive isn't validated in the full simulator — isn't that a gap?

Answer

Yes, and it's the one honest gap we're flagging ourselves rather than waiting to be caught on. The controller is complete and verified in the SIL harness — multi-lap completion, correct non-duplicated lap counting under dropout — but hasn't yet been run on a real track map in the full simulator, the step already done for Acceleration and Skidpad. It's next on the list, not blocked on anything.

NoveltyIsn't eufs_sim2 already the simulator — what did you actually build?

Answer

eufs_sim2 is the empty stage — it has no autonomy in it at all; a car sitting in it does nothing unless something publishes drive commands. We built everything that makes it drive: four mission controllers, the state estimator, the SIL test harnesses with an injectable error model, and the Monte-Carlo statistical methodology. We also found and documented four real defects in eufs_sim2 itself along the way, two of which silently break any team's first integration attempt.

RigorAre the "bugs" you found actually bugs, or just your misunderstanding?

Answer

Each one is traced to the exact line in the simulator's source, not inferred from behaviour alone — e.g. control.cpp only reads drive.acceleration/steering_angle, never drive.speed; cone_fusion.cpp constructs a publisher for the fused /cones topic but never calls it. Both produce no error message, just silent wrong behaviour, which is why we can point to the exact function and line rather than just describing symptoms.

TeamWhat did each of you individually contribute?

Answer — fill this in before tomorrow, don't leave it blank on stage

All commits currently sit under one shared identity, so have a one-line split ready per person (e.g. mission controllers / state estimation / testing & statistics) even if the git history doesn't show it — examiners ask this every time and "we all did everything" reads as unprepared, not as teamwork.

FallbackIf you get a question you don't have a clean answer for

Answer

Say what you actually know, name the boundary honestly ("that's outside what we tested"), and say what the next step to answer it would be. Every "Answer" above does exactly that — none of them claim more than the numbers support. That's the posture to keep live, too.
